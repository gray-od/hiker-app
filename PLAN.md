## 3. Осталось (в порядке работ)

**1. Питание: смена типа плана стирает дни и блюда без подтверждения.** `небольшая`
Смена типа в диалоге редактирования при непустых днях идёт тем же путём, что «применить шаблон» (`src/pages/meals/[id].tsx:453-457`), а тот удаляет все дни и блюда и собирает план заново (`:689-701`). Подтверждение есть только у отдельной кнопки «шаблон» (`:991-1002`, `:1010`).
Эффект: выбор другого типа молча стирает составленный план.

**2. Питание: откат при сбое создания не срабатывает и не проверяется.** `небольшая`
Если план уже вставлен, а шаг пересчёта итогов упал, его ошибки собираются как `{error}` (исключение не бросается) в `totalsFailure` — откат, лежащий в `catch`, не выполняется, план остаётся (`src/pages/meals.tsx:208-238, 246-249`). Сам откат (удаление плана в `meals.tsx:262-270`) результат не проверяет: `delete()` возвращает `{error}`, а не бросает, поэтому неудачная очистка не видна. Сбои на вставке дней/блюд откат запускают — там есть явные `throw` (`meals.tsx:150-152, 204-206`).
Эффект: после «ошибки создания» план-полуфабрикат остаётся в базе и всплывает в списке после перезагрузки; повторное создание даёт дубликат.

**3. Питание: созданный план не виден до перезагрузки.** `небольшая`
После создания вызывается `fetchPlans()` (`src/pages/meals.tsx:243`), который читает через кэш-первый слой `fetchUserMealPlans` (`meals.tsx:92-101`; `src/lib/cache.ts:141-155`) и возвращает старый снапшот; кэш `meals:<userId>` в файле нигде не инвалидируется.
Эффект: только что созданный план появляется в списке лишь после F5 (или когда истечёт 5-минутный TTL).

**4. Удалённый план может вернуться на экран из кэша.** `небольшая`
`meals.tsx` при удалении правит только локальный стейт (`:274-302`); `meals/[id].tsx` инвалидирует лишь `mealPlans`, не трогая `mealPlanDetail(id)` и `meals-light:<uid>` (`:535-559`, инвалидация на `:552`). Корректный образец — `deleteList` (`src/lib/supabase/service.ts:329-342`, три ключа).
Эффект: до 5 минут удалённый план снова показывается из кэша (detail-страница; он же остаётся в выборе linked-plan — `src/pages/lists/[id].tsx:68, 703-705`).

**5. Очередь не различает пользователей.** `небольшая`
`syncQueue` перебирает все записи без фильтра (`src/lib/offline-queue.ts:46-69`, выборка на `:51`), вызов из `src/components/AppShell.tsx:22-31`; поле и индекс `userId` существуют (`offline-queue.ts:11, 23`), но при replay не используются.
Эффект: на общем устройстве чужие записи под другой сессией не применяются (RLS) и застревают в очереди навсегда.

**6. M1: лимит AI 15 сообщений в день не работает.** `средняя`
У `ai_usage` нет ни одного `GRANT` (`supabase/migrations/00005_ai_usage_rate_limit.sql:1-25`; сравнить с явными грантами в `00002_grant_authenticated.sql:2-11`), код не читает ошибки: select без `error` (`src/pages/api/chat.ts:104-117`), upsert без проверки результата (`chat.ts:761-774`), в UI счётчик читается тем же путём и всегда 0 (`src/components/ChatWidget.tsx:90-96`, бейдж `:179-183`). Проверено по прод-БД: DML на `ai_usage` нет ни у `anon`/`authenticated`, ни у `service_role`.
Эффект: счётчик всегда 0, после 15 сообщений отправка не блокируется. Сначала — миграция с `GRANT` (только по отдельному подтверждению владельца), затем проверки ошибок.

**7. Пустой список исчезает из «Списков» после перезагрузки.** `небольшая`
`fetchUserLists` использует `list_items!inner` (`src/lib/supabase/service.ts:96`) — список без позиций не попадает в выборку.
Эффект: созданный пустой список виден сразу, но после перезагрузки пропадает из `/lists` и с главной (`src/pages/lists.tsx:58`, `src/pages/index.tsx:42`).

**8. Погода: дата похода не используется, результат не сохраняется.** `средняя`
Аргумент `tripDate` не используется, запрос всегда `current=` (`src/lib/gpx-weather.ts:1, 4`); полученная погода кладётся только в локальный стейт (`src/pages/lists/[id].tsx:167-171`, `:467-476`), в БД ещё до её получения записывается `weather: null` (`:444-456`).
Эффект: показывается сегодняшняя погода как «на дату похода»; после F5, на печати и у AI-помощника погоды нет (`src/pages/api/chat.ts:357-360` читает `gpx_data.weather`).

**9. Поиск в помощнике: неверный ключ выглядит как «ничего не найдено».** `небольшая`
Провайдеры парсят JSON без проверки `res.ok` (`src/lib/search-providers.ts:37, 54, 71, 88, 105, 125, 133`), пустой результат превращается в «No search results found» (`:25-30`); `runUserSearch` перехватывает только исключения (`:168-170`). Для сравнения: `validateSearchKey` статус проверяет (`:246-248`).
Эффект: при неверном/просроченном ключе помощник отвечает «ничего не найдено» вместо «поиск недоступен».

**10. Мелочи.** `небольшая` (каждая)
- Экран восстановления показывает служебный код вопроса: хранится код (`src/pages/login.tsx:105`), отдаётся как есть (`src/pages/api/auth/lookup.ts:33-39`), выводится без перевода (`src/pages/forgot-password.tsx:55, 186`; подписи вопросов — `login.tsx:67-73`).
- Сбой записи в офлайн-очередь виден только в консоли (`src/lib/offline-queue.ts:37-43`) — мутация теряется молча.
- Прямой `getUser()` без ограничения по времени может заморозить действие при «мёртвой» сети: `meals.tsx:94, 108`, `settings.tsx:122, 234, 500`, `ChatWidget.tsx:80` (страницы при этом грузятся через `resolveUser`).
- После удаления аккаунта `signOut()` вызывается без офлайн-фолбэка (`settings.tsx:149-151`; ср. `clearStoredSession` в `Navbar.tsx:48-67`).
- Сериализация cookie теряет очистку `Max-Age=0`: `if (options?.maxAge)` не пропускает ноль (`api/chat.ts:59-68`, `api/auth/callback.ts:30-39`).
- `handleDeleteList` при сбое показывает только верхний баннер без toast, а `queued`-ответ офлайн-удаления обрабатывает как ошибку (`lists/[id].tsx:182-203`; ср. соседние обработчики, например `:368-380`).

**11. Офлайн-очередь для планов питания.** `крупная`
Мутации `meal_*` идут мимо `service.ts` прямыми вызовами клиента (`meals.tsx:115-127, 144-148, 200-236, 279-282`; `meals/[id].tsx:323-354, 432-441, 542-545, 692-772`), очереди и инвалидации кэша там нет; `service.ts` очередит только gear/food/lists (`:215-417`).
Эффект: офлайн-правки планов после возврата сети не дозаписываются — их приходится повторять вручную.

## 4. Мусор/гигиена репозитория

- `user_security` и `keepalive` есть в прод-БД, но файла миграции нет ни для одной (в `supabase/migrations` — 9 файлов, 00001–00009; эти таблицы там не упоминаются) — окружение с нуля по репозиторию не соберётся.
- `supabase/migrations/00005_ai_usage_rate_limit.sql` создаёт `ai_usage` без `GRANT` — вопреки шаблону `00002_grant_authenticated.sql:2-11`; из-за этого лимит не работает (п. 6), а `supabase db reset` воспроизведёт поломку.
- `.opencode/` добавлен в `.gitignore` (строка 54) — локальный инструментарий, в репозиторий не попадает.

## 5. Чего не трогаем (осознанные решения)

- Письма и подтверждение почты: без своего домена SMTP нет — `autoconfirm: true`, сброс пароля через контрольный вопрос; отдельных работ в этом плане нет.
- Ответ на контрольный вопрос сверяется строго, без нормализации (`api/auth/recover.ts:53`) — сознательно отложено.
- Для email без записи возвращается вопрос-заглушка (`api/auth/lookup.ts:33-37`) — защита от определения существования аккаунта.
- HTML страниц не прекешируется сборкой: документы кэшируются по визитам и прогревом (`src/sw.ts:72-94`, `src/lib/prewarmRoutes.ts:146-173`) — офлайн доступно то, что посещалось.
- Офлайн — про чтение: очередь закрывает gear/food/lists/list_items; meals/settings пишут напрямую — это работа п. 11, а не регресс.
